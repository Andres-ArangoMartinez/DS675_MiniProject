# 3. Top 5 en detalle

## 1. Gas Sensor Array under Dynamic Gas Mixtures

### Qué representa físicamente

Es un experimento real de laboratorio en el que 16 sensores químicos están expuestos continuamente a mezclas variables de gases. Se realizaron dos experimentos de unas 12 horas: ethylene + methane y ethylene + CO. Los sensores se muestrearon a **100 Hz** mientras las concentraciones cambiaban a intervalos aleatorios de aproximadamente 80–120 segundos. citeturn930493search0turn371896search0

Eso es casi exactamente lo que queremos cuando hablamos de un **sistema dinámico no lineal con memoria**: la concentración cambia y los sensores no responden instantáneamente.

### Problema supervisado recomendado

No usaría simplemente:

\[
S(t)\rightarrow C(t)
\]

como único experimento.

Propondría:

\[
\boxed{
[S(t),S(t-1),...,S(t-L)]
\rightarrow
C_{CO}(t)
}
\]

como **dynamic soft sensor**.

Una extensión:

\[
[S(t),...,S(t-L)]\rightarrow C_{CO}(t+h)
\]

para estudiar distintos horizons.

### X

Los 16 canales de sensores químicos, con:

- valores actuales,
- lags,
- diferencias \(S_t-S_{t-k}\),
- rolling means,
- rolling slopes.

### y

Elegiría inicialmente:

**CO concentration [ppm]** en `ethylene_CO`.

Después podría repetirse con ethylene.

No recomiendo empezar con multi-output porque complica el análisis sin aumentar necesariamente el valor del Milestone 1.

### ¿Lags?

**Sí, absolutamente.**

La propia motivación del dataset es que los sensores tienen respuesta lenta frente a cambios rápidos de concentración. El dataset fue publicado para investigar continuous monitoring y mejorar response time. citeturn957098search1

Aquí la pregunta científica natural es:

> ¿Cuánto mejora la estimación de concentración cuando el modelo conoce el historial reciente de los sensores?

Eso es excelente para DS675.

### Horizon

Para estimación de concentración:

- \(h=0\): soft sensing actual.
- \(h=1\) s.
- \(h=5\) s.
- \(h=10\) s.

No comenzaría con horizontes enormes.

### Modelos

Una secuencia muy adecuada al curso:

1. Linear / Ridge Regression.
2. KNN Regression.
3. Random Forest.
4. Gradient Boosting / XGBoost si se permite.
5. SVR en un subset.
6. Opcional: MLP/LSTM al final.

### Split correcto

**Nunca random row split.**

A 100 Hz, dos filas consecutivas están separadas sólo 0.01 s.

Un random split permitiría que una observación a \(t\) quede en train y la de \(t+0.01\) en test.

Eso produciría un test artificialmente fácil.

Usaría bloques cronológicos:

**Train:** first 60%  
**Validation:** next 20%  
**Test:** last 20%

y colocaría un **gap** de al menos el tamaño máximo de las lag windows.

### Kaggle activity

Tiene aproximadamente **9 notebooks, 1 discussion y ~2,800 downloads**: suficiente actividad para revisar trabajos existentes, pero muy lejos del nivel de saturación de Titanic, C-MAPSS o Electric Motor Temperature. citeturn930493search4turn930493search0

Este es exactamente el tipo de actividad intermedia que buscabas.

### Debilidad habitual

La mayor amenaza metodológica es evaluar los millones de filas como si fueran observaciones IID.

No lo son.

La muestra independiente efectiva es muchísimo menor debido a la autocorrelación temporal.

### Tres extensiones originales

1. **Static vs dynamic representation:** current sensors vs sensors + history.
2. **Lag-window sensitivity:** 0.5, 1, 2, 5, 10 seconds.
3. **Prediction horizon sensitivity:** \(h=0,1,5,10\) sec.
4. Sensor-ablation study.
5. Linear vs nonlinear performance.
6. Train on one operating section → evaluate on another.

### Viabilidad

**Excelente para un semestre.**

Además, no es necesario entrenar usando los 4.18M puntos. Se puede downsample de manera físicamente razonable —por ejemplo de 100 Hz a 5–10 Hz— después de estudiar la dinámica.

### Mi evaluación

**Mejor candidato global.**

# 2. Electric Motor Temperature — PMSM

### Sistema físico

Son mediciones experimentales de un **Permanent Magnet Synchronous Motor** en test bench. Hay 185 horas de funcionamiento, muestreo a 2 Hz y múltiples sesiones identificadas mediante `profile_id`. Incluye `u_d`, `u_q`, `i_d`, `i_q`, motor speed, torque, coolant, ambient y varias temperaturas. citeturn930493search3turn930493search7

### Problema recomendado

\[
\boxed{
X_{t-L:t}\rightarrow T_{PM}(t+h)
}
\]

donde \(T_{PM}\) es la temperatura del permanent magnet/rotor.

Esto tiene una interpretación muy atractiva:

> Construir un **virtual temperature sensor** capaz de estimar o anticipar una temperatura interna difícil de medir.

### X

Primera versión:

- `u_d`
- `u_q`
- `i_d`
- `i_q`
- `motor_speed`
- `torque`
- `coolant`
- `ambient`

No usaría `profile_id` como predictor; es un **group identifier**.

Luego puede compararse añadiendo temperaturas del stator.

### y

`pm`

### Lags

Sí.

Un motor tiene **inercia térmica**. La temperatura actual no depende sólo de corriente o torque instantáneos sino de la energía disipada durante minutos anteriores.

Aquí hay una excelente comparación:

\[
X_t\rightarrow T_{PM,t}
\]

vs.

\[
X_{t-L:t}\rightarrow T_{PM,t}
\]

vs.

\[
X_{t-L:t}\rightarrow T_{PM,t+h}
\]

### Horizons

Yo probaría:

- current temperature,
- +30 sec,
- +2 min,
- +5 min.

### Modelos

1. Linear / Ridge.
2. KNN Regressor.
3. Random Forest.
4. Gradient Boosting.
5. Neural network como extensión.

### Split correcto

Aquí existe una oportunidad metodológica particularmente buena.

**No mezclar filas del mismo `profile_id` entre training y testing.**

Se debe hacer algo como:

- train profiles: ~60%
- validation profiles: ~20%
- test profiles: ~20%

con `GroupShuffleSplit` o grupos elegidos deliberadamente.

Así el modelo debe generalizar a **operating sessions que nunca vio**.

### Kaggle work existente

Este dataset sí tiene mucha actividad: actualmente alrededor de **96 notebooks, 31 discussions y más de 31,000 downloads**. Hay notebooks de regression, rotor-temperature prediction, baseline estimation e incluso trabajo reciente con physics-informed networks. citeturn930493search6turn328967search5turn328967search7turn328967search17

### Por qué todavía lo consideraría

Muchos trabajos plantean simplemente:

\[
X_t\rightarrow T_t
\]

como tabular regression.

Esa formulación ignora una gran parte de la estructura física.

Incluso trabajos publicados sobre este dataset han empleado `train_test_split` sobre observaciones; si no se separan las sesiones adecuadamente, pueden mezclarse operating profiles entre train y test. citeturn675547search10

Por ello tu contribución podría ser:

> **How much of the reported PMSM temperature-prediction accuracy survives when validation is performed across unseen operating profiles and the dynamic thermal history is modeled explicitly?**

Esa es una pregunta mucho más fuerte que “probar Random Forest”.

### Extensiones originales

1. Random split vs profile-aware split.
2. Static vs lagged feature representation.
3. Prediction horizons 0–5 min.
4. Persistence baseline:
   \[
   \hat T(t+h)=T(t)
   \]
5. Thermal feature engineering, por ejemplo \(i_d^2+i_q^2\).
6. Performance by speed/torque operating regime.

### Viabilidad

**Excelente.**

Probablemente es el proyecto con mejor aspecto en un portfolio técnico.

# 3. SWaT — Secure Water Treatment

SWaT es una planta de tratamiento de agua a escala realista con seis etapas y sensores de flow, tank level, pressure, pH/conductivity y actuadores como pumps y valves. Aunque suele usarse para cybersecurity/anomaly detection, yo **no haría ése el proyecto principal**.

### Formulación DS675 que prefiero

Por ejemplo:

\[
\boxed{
X_{t-60:t}\rightarrow LIT101(t+30)
}

Predicción del tank level de Stage 1 treinta segundos adelante.

X puede incluir:

- `FIT101`
- `MV101`
- `P101/P102`
- `LIT101`
- variables aguas arriba/abajo
- lags y rolling features.

Eso lo convierte directamente en **data-driven dynamic modeling**.

Después:

> ¿Se degrada el modelo cuando el sistema entra en attack/fault conditions?

Eso sería una extensión muy interesante.

### Modelos

- Linear/Ridge
- KNN
- Random Forest
- Gradient Boosting
- opcional LSTM

### Split

Éste es un problema frecuente en anomaly detection.

### Existing work

2. Static vs dynamic ML.

### Viabilidad

**Alta**, pero exige controlar bien el scope.

# 4. Condition Monitoring of Hydraulic Systems

Este es particularmente bueno para un proyecto de **sensor-based condition monitoring**.

El banco hidráulico repite ciclos de carga de 60 segundos mientras se miden pressures, flows, temperatures, vibration y otras señales. Hay **2,205 ciclos**, pero cada ciclo contiene mediciones multirate: sensores a 1, 10 y 100 Hz, para un total equivalente a **43,680 raw values por ciclo**. Los labels incluyen cooler condition, valve condition, pump leakage y accumulator pressure. citeturn972713search0turn972713search6

### Problema recomendado

Por ejemplo:

\[
\boxed{
\text{sensor waveform during 60-s cycle}
\rightarrow
\text{valve condition}
}
\]

Classes:

100, 90, 80, 73%.

### X

En lugar de usar 43,680 columnas directamente, construir:

- mean
- std
- min/max
- RMS
- percentiles
- slope
- peak-to-peak
- early/late cycle means

por sensor.

Luego comparar contra una representación temporal más rica.

### y

`valve condition`.

Luego se puede repetir con pump leakage.

### Lags

Aquí haría una distinción:

**lags dentro del ciclo: sí.**

**lags de ciclos anteriores: no necesariamente.**

Los estados de componentes fueron experimentalmente establecidos; no es una degradación natural continua.

### Modelos

- Logistic Regression
- KNN
- Decision Tree
- Random Forest
- SVM
- Gradient Boosting

Muy alineado con DS675.

### Split

La unidad independiente es el **cycle**, no cada punto de sensor.

Nunca dividir samples dentro de un mismo 60-second cycle entre train y test.

### Existing Kaggle work

La actividad es razonable y todavía limitada. Kaggle muestra notebooks de basic EDA/resampling y un trabajo bastante popular con LSTM-autoencoder y clasificación de cooler, valve, pump y accumulator condition. citeturn751126search1turn751126search4

Eso es favorable: tienes trabajo previo para criticar, pero no cientos de notebooks.

### Originalidad

1. Raw/summary/static features vs dynamic temporal features.
2. Multi-sensor ablation.
3. KNN scaling sensitivity.
4. PCA before KNN/SVM.
5. Separate model per fault vs multi-output model.

### Riesgo

2,205 ciclos no es enorme.

Es suficiente para ML clásico, pero no invita naturalmente a deep learning masivo.

### Viabilidad

**Muy alta para DS675**, especialmente si Houle prefiere que el proyecto use varios algoritmos clásicos.

# 5. Tennessee Eastman Process

Desde control/system identification, probablemente es el dataset más cercano a tus intereses.

TEP representa un proceso químico integrado con reactor, separator, compressor, stripper y recycle. El dataset de Rieth tiene **500 simulation runs por condición**, 41 process measurements y 11 manipulated variables. Las muestras están separadas por tres minutos. citeturn149468search0turn675547search11

### Pero hay un problema

TEP es probablemente **el benchmark de fault detection más estudiado de process systems**.

Incluso estudios recientes siguen benchmarkeando decenas de anomaly-detection algorithms sobre él. citeturn675547search5turn675547search4

Por eso no recomendaría otro:

> PCA vs Autoencoder vs LSTM for TEP fault detection.

Sería difícil defender originalidad.

### La forma de hacerlo interesante

Usarlo como **dynamic system identification / output prediction**.

Por ejemplo:

\[
\boxed{
[XMV_{t-L:t}, XMEAS_{t-L:t}]
\rightarrow
XMEAS_9(t+h)
}
\]

donde `XMEAS(9)` es reactor temperature.

O seleccionar:

- reactor pressure,
- separator pressure,
- compressor work,
- product-related variable.

### Comparación

Static:

\[
X_t\rightarrow y_{t+1}
\]

Dynamic:

\[
X_{t-L:t}\rightarrow y_{t+1}
\]

y multi-step:

\[
X_{t-L:t}\rightarrow y_{t+5}
\]

### Split

Aquí es crucial dividir por:

**`simulationRun`**

y no por filas.

De lo contrario, train/test contendrían fragmentos del mismo simulated trajectory.

### Modelos

- Linear Regression
- Ridge
- KNN
- Random Forest
- Gradient Boosting
- SVR

### Existing Kaggle work

El Kaggle dataset tiene alrededor de 15 notebooks y existen notebooks populares específicamente de fault detection/anomaly detection. citeturn149468search0turn751126search10

La investigación académica, sin embargo, está mucho más saturada que la actividad de Kaggle sugiere.

### Originalidad

1. Prediction en vez de detection.
2. Inputs-only vs inputs + output-history.
3. One-step vs multi-step.
4. Performance by fault/operating regime.
5. Linear vs nonlinear identification.

### Viabilidad

Técnicamente **excelente**, pero tendría que explicar a Houle explícitamente cuál es la contribución que lo diferencia de décadas de TEP research.

# 1. WADI — probablemente el sucesor natural de SWaT

urlWADI en Kagglehttps://www.kaggle.com/datasets/giovannimonco/wadi-data

Si SWaT te llamó la atención, **WADI debería estar muy arriba en tu lista**.

WADI fue desarrollado por el mismo ecosistema de iTrust y representa una red de distribución de agua a escala física. Tiene **16 días de operación continua: 14 normales y 2 con ataques**, y registra **123 sensores y actuadores**. El sistema está organizado en subprocesses con PLC, bombas, válvulas, tanques, presión, caudal y otras variables. La versión disponible en Kaggle tiene alrededor de 1.2 millones de registros y 261 columnas en los archivos publicados. citeturn877286search0turn877286search2turn918599search4

Conceptualmente se parece mucho más a un sistema SCADA real:

\[
\text{PLC}
\rightarrow
\text{Pump/Valve}
\rightarrow
\text{Physical Process}
\rightarrow
\text{Flow/Pressure/Level}
\rightarrow
\text{PLC}
\]

Eso es exactamente lo que queremos.

### Formulación que me interesa

En lugar de hacer simplemente:

\[
X_t\rightarrow Attack_t
\]

haría primero **modelado del proceso físico**:

\[
\boxed{
X_{t-60:t}\rightarrow L_{tank}(t+30)
}
\]

o

\[
X_{t-60:t}\rightarrow P(t+30)
\]

donde \(X\) contiene:

- valve states,
- pump states,
- flows,
- pressures,
- tank levels,
- históricos de esas variables.

Después puedes usar el **residual de predicción**

\[
e(t)=y(t)-\hat y(t)
\]

como indicador de comportamiento anormal.

Ahí ya estás acercándote conceptualmente a **model-based fault detection**, pero usando ML.

### Proyecto particularmente interesante

**Static vs Dynamic Machine Learning for SCADA Process Modeling**

Comparar:

\[
X_t\rightarrow y_{t+30}
\]

contra

\[
[X_t,X_{t-1},...,X_{t-k}]
\rightarrow y_{t+30}
\]

con:

- Linear/Ridge
- KNN
- Random Forest
- Gradient Boosting

Esto está extremadamente bien alineado con DS675.

### Riesgo

La mayoría de la literatura WADI está orientada a **cyberattack/anomaly detection**. Si simplemente reproduces esa clasificación, entrarías en un área bastante transitada. citeturn877286search6turn877286academia24

La oportunidad está en **tratarlo como proceso dinámico controlado**, no como dataset de cybersecurity.

### Mi nota

**9.5/10 para tus intereses.**

# 2. HAI — posiblemente el más interesante desde SCADA/DCS/control

urlHAI Security Dataset en Kagglehttps://www.kaggle.com/datasets/icsdataset/hai-security-dataset

Este apareció mucho más fuerte después de aplicar tu nuevo criterio.

HAI significa **HIL-based Augmented Industrial Control System**. El testbed combina cuatro procesos:

- boiler,
- turbine,
- water treatment,
- Hardware-in-the-Loop power simulation.

Pero lo verdaderamente interesante es el hardware/control detrás.

El boiler usa **Emerson Ovation DCS**, el turbine process usa **GE Mark VIe DCS**, el water-treatment process un **Siemens S7-300 PLC**, y el HIL está interconectado mediante Siemens S7-1500/ET200 y OPC. Además, los procesos fueron conectados para generar variables físicamente acopladas. citeturn918599search1turn743571search6

Esto es mucho más cercano a un ambiente industrial SCADA/DCS que prácticamente cualquier dataset clásico de Kaggle.

## ¿Por qué me gusta?

Porque no tenemos sólo:

\[
Sensor\rightarrow Label
\]

Tenemos algo parecido a:

\[
\text{controllers}
+
\text{actuators}
+
\text{physical states}
+
\text{feedback loops}.
\]

Y las series son continuas en el tiempo. Las versiones recientes contienen decenas de tags SCADA y cientos de horas de operación normal y anómala. citeturn918599search1

## Formulación A — system modeling

Seleccionar uno de los subsistemas, por ejemplo water treatment:

\[
\boxed{
[u(t-k:t),y(t-k:t)]
\rightarrow
y(t+h)
}
\]

Ejemplo conceptual:

\[
\text{pump/valve commands + historical level/flow}
\rightarrow
\text{future water level}
\]

Esto sería casi un **black-box system identification problem**.

## Formulación B — predictive fault detection

Otra posibilidad:

\[
X_{t-k:t}\rightarrow
P(\text{abnormal condition in next }h)
\]

que es más interesante que simplemente identificar un ataque que ya está ocurriendo.

## Formulación C — residual-based diagnosis

Entrenas el modelo sólo sobre comportamiento normal:

\[
\hat y(t+1)=f(X_{t-k:t})
\]

y calculas:

\[
r(t)=y(t)-\hat y(t).
\]

Después:

\[
r(t)\rightarrow\text{normal/fault}
\]

Esto tiene una conexión preciosa con **Fault Detection and Isolation (FDI)**.

## Actividad Kaggle

Curiosamente está bastante bien situado para tu criterio: Kaggle muestra alrededor de **8 notebooks y ninguna discusión**, mientras el dataset tiene documentación formal, competiciones HAICon y resultados publicados fuera de Kaggle. citeturn918599search6turn918599search1

Es decir:

**documentación científica fuerte + Kaggle no saturado.**

### Riesgo

Es complejo.

Tendríamos que escoger **un subsystem**, no modelar todo HAI.

### Mi nota

**9.5/10.**

Para portfolio orientado a control/automation/industrial ML incluso me gusta más que WADI.

# 3. PRONTO Heterogeneous Benchmark

urlPRONTO en Kagglehttps://www.kaggle.com/datasets/afrniomelo/pronto-benchmark

Este es uno de los descubrimientos más interesantes de esta nueva búsqueda.

PRONTO proviene de una **industrial-scale multiphase flow facility** y fue diseñado explícitamente para:

- process monitoring,
- condition monitoring,
- fault detection,
- fault diagnosis,
- heterogeneous sensor fusion.

Contiene process measurements, alarm records, high-frequency pressure measurements, ultrasonic flow measurements y logs de operación, con múltiples operating conditions y fallas inducidas. citeturn232938search2turn232938search3

Es decir, está mucho más cerca de:

**process systems engineering + industrial control**

que de un dataset típico de ML.

## Sistema

Una instalación de flujo multifásico donde coexisten:

- gas/air,
- water,
- oil,
- separator,
- pipelines,
- pressure,
- flow,
- diferentes operating conditions.

Eso genera relaciones altamente no lineales.

## Problema DS675 que propondría

No usaría todos los datos multimodales.

Tomaría **las señales de proceso SCADA de baja frecuencia** y plantearía:

\[
X_{t-k:t}\rightarrow y_{t+h}
\]

para alguna variable clave de pressure/flow.

Luego:

\[
\text{prediction residuals}\rightarrow\text{fault state}.
\]

Alternativamente:

\[
X_{t-k:t}\rightarrow\text{fault class}.
\]

## Algo especialmente interesante

Comparar:

### Modelo estático

\[
y_t=f(X_t)
\]

### Dynamic ML

\[
y_t=f(X_t,X_{t-1},...,X_{t-k})
\]

### Fault detection

\[
r_t=y_t-\hat y_t
\]

Es casi la unión perfecta entre:

**ML + system identification + process monitoring.**

## Kaggle

El dataset tiene aproximadamente **450 downloads**, unos **6,000 views**, pero sólo **1 notebook y 1 discussion** registrados en la página que encontré. citeturn232938search2

Aquí sí hay enorme **originality headroom**.

## Problema

Es grande: Kaggle reporta unos **4.37 GB y 407 archivos**. citeturn232938search2

Eso puede ser una bendición o una maldición.

Habría que reducir deliberadamente el problema.

### Mi nota

**9.3/10 científicamente.**

**8.5/10 para facilidad de ejecución.**

# 4. DAMADICS — el más “Control Engineering” de todos

urlDAMADICS en Kagglehttps://www.kaggle.com/datasets/afrniomelo/damadics-actuator-benchmark-lublin-sugar-factory

Este me parece especialmente interesante para ti.

DAMADICS significa básicamente un benchmark para **actuator diagnosis in industrial control systems**.

El sistema es un **electro-pneumatic control valve actuator** utilizado en una fábrica de azúcar real en Lublin, Polonia.

El benchmark fue construido específicamente alrededor de:

- closed-loop operation,
- nonlinear static/dynamic behavior,
- control valves,
- servomotor,
- actuator position,
- control signals,
- pressure,
- flow,
- temperature,
- faults.

Se definieron **19 tipos de fallas**, incluyendo valve clogging, sedimentation, erosion, increased friction, external/internal leakage y fallas del servomotor/positioner. citeturn743571search0turn743571search11

Aquí no estamos buscando una interpretación de control.

**El dataset nació de control engineering.**

## Representación

Podrías conceptualizar:

\[
CV(t)\rightarrow
\text{actuator}\rightarrow
\text{valve position}\rightarrow
\text{process flow}.
\]

Con sensores adicionales:

\[
\{CV,P,T,F,Z,\ldots\}
\]

donde aparecen variables de controller output, pressures, flow y valve/rod position. citeturn743571search11

## Proyecto A

### Data-driven actuator model

\[
\boxed{
[u(t-k:t),y(t-k:t)]
\rightarrow
Z(t+1)
}
\]

con \(Z\) como valve position.

Entonces comparar:

- Linear Regression
- KNN
- Random Forest
- Gradient Boosting.

## Proyecto B

Más interesante:

### Fault detection using model residuals

Construir un modelo del actuator normal:

\[
\hat y(t)=f(u(t-k:t),y(t-k:t-1))
\]

Residual:

\[
r(t)=y(t)-\hat y(t)
\]

y posteriormente:

\[
r(t)\rightarrow \text{fault class}.
\]

Eso es **machine-learning-based FDI**.

## Originalidad

Kaggle muestra actualmente **0 notebooks y 0 discussions**. citeturn918599search2turn918599search3

Eso me genera dos reacciones.

Por un lado:

**enorme originalidad en Kaggle.**

Pero también:

hay menos recursos para comparar con Houle's “existing Kaggle work”.

Por eso no lo pongo #1.

## Otra consideración

Es antiguo —la investigación DAMADICS proviene de principios de los 2000— aunque conceptualmente sigue siendo extremadamente relevante para actuator fault diagnosis. citeturn743571search0

### Mi nota

**9.2/10 por afinidad con control.**

Probablemente es el que más disfrutarías conceptualmente.

# 5. SKAB — como un “Hydraulic mini-SWaT”

urlSKAB en Kagglehttps://www.kaggle.com/datasets/yuriykatser/skoltech-anomaly-benchmark-skab

SKAB me parece una opción que no deberíamos ignorar.

Es un testbed físico con:

- water tank,
- motor-driven water pump,
- dos solenoid valves,
- pressure sensor,
- flow sensor,
- motor current,
- motor voltage,
- pump vibration,
- motor temperature,
- fluid temperature.

Se introducen fallas físicas como cierre de válvula, aumento de temperatura y rotor imbalance. La adquisición usa OPC UA. citeturn294167search8turn294167search10

¿Te suena familiar?

Es prácticamente una intersección de:

**Hydraulic System + SWaT + predictive maintenance.**

## Variables

Entre las variables publicadas están:

\[
\begin{aligned}
&Current\\
&Voltage\\
&Pressure\\
&RateRMS\\
&Temperature\\
&Thermocouple\\
&Accelerometer1RMS\\
&Accelerometer2RMS
\end{aligned}
\]

además de:

- `anomaly`,
- `changepoint`.

citeturn294167search0turn294167search4

## Proyecto

Un enfoque directo sería:

\[
X_{t-k:t}\rightarrow anomaly_{t+h}.
\]

Pero me parece más interesante:

\[
[\text{voltage,current,valve context,history}]
\rightarrow
[\text{pressure, flow}]
\]

y utilizar las desviaciones del comportamiento esperado para fault detection.

## Ventaja enorme

Es mucho más manejable que HAI/WADI.

Hay sólo alrededor de **35 experiments** en la versión 0.9. citeturn294167search0

## Desventaja

Precisamente ése es también su problema.

Las observaciones temporales pueden ser muchas, pero sólo tenemos unas decenas de **experimentos independientes**.

Por tanto, no debemos decir:

> “tengo cientos de miles de independent observations”.

No sería cierto.

El split correcto debería ser:

\[
\boxed{\text{train experiments}\neq\text{test experiments}}
\]

no random rows.

### Mi nota

**8.9/10.**

Para un mini-project manejable, puede terminar siendo mejor que algunos datasets enormes.

# La formulación que recomiendo

## Dynamic process prediction

Tomaría **una sección física concreta**, no las 51 variables completas inicialmente.

Por ejemplo, un tanque:

\[
\boxed{
[u(t-k:t),y(t-k:t)]
\rightarrow
L(t+h)
}
\]

donde:

- \(u\) = estados de pumps/valves,
- \(y\) = level, flow, pressure, etc.,
- \(L(t+h)\) = nivel futuro del tanque.

Por ejemplo conceptualmente:

\[
\{
MV101,\,
P101,\,
P102,\,
FIT101,\,
LIT101(t-k:t)
\}
\rightarrow
LIT101(t+30s)
\]

Esto ya parece **black-box dynamic system modeling**.

---

# El experimento central que haría

Compararía tres representaciones.

### Modelo 1 — Static

\[
X_t\rightarrow y_{t+h}
\]

### Modelo 2 — Dynamic

\[
[X_t,X_{t-1},...,X_{t-k}]
\rightarrow y_{t+h}
\]

### Modelo 3 — Dynamic + engineered features

Agregar:

- rolling mean,
- rolling std,
- rate of change,
- valve/pump transition indicators,
- accumulated pump-on time.

Y comparar:

- Linear/Ridge Regression
- KNN Regressor
- Decision Tree
- Random Forest
- Gradient Boosting
- opcional RNN al final.

Eso conecta de manera casi perfecta con el curriculum.

# Lo realmente interesante

Después de modelar operación normal:

\[
\hat y(t+h)=f(X_{t-k:t})
\]

podrías calcular:

\[
r(t)=
y(t)-\hat y(t)
\]

y estudiar si durante ataques:

\[
|r(t)|\uparrow
\]

Es decir:

### ML dynamic model → residual → anomaly indicator

Eso conecta tu background de control con ML sin convertir el proyecto en control clásico.

---

## Validación correcta

Aquí hay un peligro enorme.

**Random train/test split sería metodológicamente incorrecto.**

A 1 Hz:

\[
x_t
\quad\text{y}\quad
x_{t+1}
\]

son casi la misma condición física.

Si uno termina en train y el otro en test, el desempeño parece artificialmente excelente.

Yo usaría:

\[
\text{Train}
\rightarrow
\text{Validation}
\rightarrow
\text{Test}
\]

como bloques cronológicos.

Además añadiría un **gap** igual o mayor que la largest lag window.

---

## Otro baseline imprescindible

Para level/temperature/pressure:

\[
\boxed{
\hat y(t+h)=y(t)
}
\]

Persistence model.

Porque si el tanque cambia lentamente, un Random Forest con \(R^2=0.999\) puede parecer impresionante cuando simplemente decir:

> “dentro de 10 segundos será casi igual que ahora”

obtiene \(R^2=0.998\).

Este baseline sería una de las cosas que haría tu trabajo mucho más riguroso.

- PLC + actuadores + sensores.
- Variables con significado físico.

# El problema

La estructura publicada es principalmente:

\[
\text{measured signals}
\rightarrow
\text{anomaly}
\]

No tenemos en cada CSV el mismo nivel de información explícita de:

\[
u(t)=

\]

### Condition monitoring / fault detection

que para:

# Tamaño efectivo

SKAB v0.9 contiene aproximadamente **35 archivos experimentales**, y cada archivo representa un experimento con una anomalía. citeturn830661search3turn569244search3

Esto es crucial.

Podemos tener miles de timestamped rows.

Pero no debemos fingir que son miles de fallas independientes.

En realidad aproximadamente:

\[
N_{\text{events}}\sim35
\]

Eso limita bastante supervised fault prediction.

---

# Una formulación posible

Podríamos hacer:

\[
X_{t-k:t}
\rightarrow

\]

Pero aparece un problema.

Supongamos que dividimos aleatoriamente filas de un mismo experimento.

Entonces:

- parte del mismo valve-closing experiment está en train,
- otra parte está en test.

Eso mide interpolación dentro del experimento.

No generalización a una falla nueva.

---

# Split correcto

Deberíamos hacer:

\[
\boxed{
\text{train experiments}
\neq
\text{test experiments}
}
\]

No:

\[
\text{random rows}
\]

Esto probablemente bajaría muchísimo los scores respecto a algunos análisis ingenuos.

o:

Podemos estudiar el comportamiento del pump loop.

Pero sigue faltando un verdadero manipulated input.

Por eso la interpretación system identification es más débil.

## Pros SKAB

- Testbed físico.
- Faults físicos auténticamente interesantes.
- Pump + hydraulic loop.
- Pressure, flow, vibration, electrical variables.
- Muy interpretable.
- Small/manageable.
- Excelentes labels.
- `changepoint` además de `anomaly`.
- Múltiples tipos de failure.
- Ideal para feature engineering.
- Ideal para PCA.
- Ideal para classification.
- Existe leaderboard y notebooks para comparar.
- Buen ejemplo de predictive maintenance.

## Contras

- Sólo ~35 experiments.
- Pocos eventos independientes.
- Mucha menos riqueza SCADA.
- No hay manipulated/control input explícito comparable con SWaT.
- Más condition monitoring que process control.
- Ya tiene benchmarks anomaly detection muy establecidos.
- Supervised early-warning prediction es difícil con tan pocos eventos.
- Random row splits serían particularmente engañosos.
- Menor profundidad para multivariable process modeling.

### Evaluación

\[
\boxed{\textbf{81/100}}
\]

No es un mal proyecto.

Simplemente **no es el mejor de estos cuatro para la dirección que quieres tomar**.

Mi recomendación cambia mucho dependiendo de qué quieres que sea el corazón del proyecto.

X_t\rightarrow Attack
\]

\[

Pero **no escogería esta dirección** para ti.

### Si hacemos:

[u_{t-k:t},y_{t-k:t}]

\]

entonces:

\[
\boxed{
SWaT
\approx
BATADAL
>
WADI
\gg
SKAB
}
\]

Y ésa es la dirección que considero más interesante.

# Mi propuesta para cada uno

| Dataset | Pregunta de proyecto que realmente usaría |
|---|---|
| **SWaT** | ¿Cuánto mejora la predicción de niveles/flows futuros al incorporar la historia temporal de sensores y actuadores? |
| **BATADAL** | ¿Pueden modelos ML aprender la dinámica hidráulica normal de una red SCADA y usar errores de predicción para revelar anomalías? |
| **WADI** | ¿Qué tan bien generalizan modelos estáticos vs dinámicos para predecir estados de reservoirs bajo diferentes demandas operativas? |
| **SKAB** | ¿Puede la historia multivariada de sensores anticipar cambios de condición/fallas de una bomba hidráulica? |

Fíjate en algo: las primeras tres tienen una formulación natural de **entrada–salida**.

SKAB tiene una formulación natural de **condition → failure**.

Ahí está la diferencia.

# Mi decisión entre SWaT y BATADAL

Ésta es probablemente la decisión importante.

## Escogería SWaT si queremos:

- testbed físico,
- PLC real,
- fast dynamics,
- mayor riqueza,
- mayor valor portfolio,
- posible evolución a RNN,
- normal + abnormal dynamics.

El proyecto sería:

> **Machine-Learning-Based Dynamic Modeling of a SCADA-Controlled Water Treatment Process**

con un subsystem concreto.

---

## Escogería BATADAL si queremos:

- proyecto extremadamente limpio,
- dataset pequeño pero suficiente,
- variables muy claras,
- computational experiments rápidos,
- splits temporales claros,
- lag engineering fácilmente interpretable,
- menor probabilidad de perdernos en preprocessing.

El proyecto sería:

> **Data-Driven Dynamic Modeling of a SCADA Water Distribution Network Using Machine Learning**

Y tiene una ventaja pedagógica enorme: con BATADAL podemos dedicar el esfuerzo a **Machine Learning**, que es justamente la materia del curso.

La diferencia es suficientemente pequeña como para que convenga decidir mirando los datos reales, no sólo la descripción.

El paso que más valor tendría ahora es hacer precisamente eso: **abrir SWaT y BATADAL, reconstruir sus variables como \(u\), \(y\), states/disturbances, escoger 2–3 targets concretos y diseñar los experimentos de lags/horizon/splits.** Ahí podremos saber cuál produce el proyecto de DS675 más sólido antes de comprometernos con uno.
