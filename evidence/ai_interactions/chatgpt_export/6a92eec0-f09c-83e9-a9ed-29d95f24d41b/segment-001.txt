- Mini-quiz de 8 preguntas con corrección y explicación inmediata.
- Checklist de dominio y barra de progreso.
- Área de notas de recuperación que se conserva localmente en el navegador.

Sí. Con base **solo en lo que explicó el profesor en ambos transcripts**, el mini-project es un proyecto progresivo de **Machine Learning supervisado y predictivo** que empieza de manera individual y termina en grupo.

La idea general es esta:

> **Dataset real → entender el problema → investigar qué se ha hecho → formar equipo → construir y evaluar modelos → presentar resultados.**

Kaggle juega un papel central, pero **no como lugar para copiar soluciones**. Se usa como fuente de datasets, como repositorio de trabajos previos y como referencia para desarrollar criterio profesional.

## Qué tienes que hacer en el mini-project

El proyecto está dividido en **4 milestones**.

### Milestone 1 — Explorar y proponer datasets
Trabajo **individual**.

Tienes que ir a **Kaggle** y escoger **dos datasets candidatos** que podrían servir para un proyecto de Machine Learning supervisado.

Para cada dataset debes entender y describir cosas como:

- qué datos contiene,
- aproximadamente cuántos ejemplos tiene,
- qué variables/features tiene,
- cuál podría ser la variable que quieres predecir,
- qué tipo de problema predictivo podrías plantear,
- si parece adecuado para entrenar y evaluar modelos.

El profesor insiste en algo importante: **no todo dataset de Kaggle sirve**.

Por ejemplo, un dataset puede servir para hacer visualizaciones o EDA, pero no necesariamente para predictive ML.

Para que sea apropiado debería existir algo parecido a:

\[
X \rightarrow y
\]

donde:

- \(X\) = variables predictoras,
- \(y\) = target/label que quieres predecir.

Ejemplo sencillo:

| Age | Income | Debt | Default |
|---|---:|---:|---|
| 32 | 80000 | 10000 | No |
| 46 | 55000 | 35000 | Yes |

Podrías plantear:

\[
Age,\ Income,\ Debt \rightarrow Default
\]

Entonces `Default` sería el target y las otras columnas serían predictors.

El profesor también advierte que el dataset debe tener **suficientes observaciones**. Dio como ejemplo que algo con alrededor de **100 registros podría ser demasiado pequeño** para hacer training/test de manera convincente.

Al final de este milestone recibes feedback del profesor sobre la calidad y viabilidad de tus opciones.

# Milestone 2 — Investigar qué se ha hecho con el dataset

También es **individual**.

Después del feedback del Milestone 1, eliges **uno de los dos datasets**.

Ahora Kaggle cambia de función.

Ya no estás buscando simplemente el dataset.

Estás investigando:

> **¿Qué han hecho otras personas con este mismo dataset?**

Buscas notebooks, analyses y modelos publicados en Kaggle.

Por ejemplo:

- qué algoritmos usaron,
- qué preprocessing hicieron,
- qué variables utilizaron,
- qué performance obtuvieron,
- qué métricas utilizaron,
- qué approaches parecen funcionar,
- qué approaches parecen débiles o incorrectos.

Aquí el profesor quiere que desarrolles **juicio crítico**.

No debes pensar:

> “Está en Kaggle, por lo tanto está bien.”

De hecho, dijo explícitamente que en Kaggle vas a encontrar trabajos:

- excelentes,
- mediocres,
- y algunos directamente malos.

El objetivo es que seas capaz de decir algo como:

> “This approach achieved high accuracy, but the evaluation may be unreliable because the preprocessing appears to use information from the full dataset before the train-test split.”

Ese tipo de razonamiento es precisamente el tipo de juicio profesional que quiere que desarrolles.

# El problema de escoger un dataset demasiado popular

Aquí el profesor dio una recomendación muy útil.

No recomienda elegir necesariamente el dataset con más notebooks o discusiones.

Idealmente busca uno con **actividad intermedia**.

¿Por qué?

Porque si eliges algo extremadamente popular, posiblemente ya hayan probado:

- logistic regression,
- random forests,
- SVM,
- neural networks,
- gradient boosting,
- extensive feature engineering,
- hyperparameter tuning,
- ensembles,
- etc.

Entonces puede ser difícil hacer una contribución propia.

El proyecto tiene un componente relacionado con:

> **contribution and originality**

No basta con decir:

> “Encontré este notebook de Kaggle, corrí lo mismo y obtuve resultados similares.”

Eso tendría poca originalidad.

Pero tampoco quieres necesariamente el extremo contrario:

> dataset con prácticamente cero análisis.

Puede ser señal de problemas como:

- dataset demasiado pequeño,
- datos incompletos,
- target poco claro,
- mala calidad,
- dataset diseñado para EDA pero no para prediction,
- poca información útil para construir un modelo.

Por eso la zona ideal sería algo así:

```text
Muy popular                    Intermedio                    Sin actividad
───────────────|────────────────────────────────|──────────────────
Difícil ser     ← IDEAL                       Puede haber
original                                      problemas
```

### 5. Comparar modelos

No es suficiente correr un modelo.

La lógica debería ser algo como:

```text
Model A
vs.
Model B
vs.
Model C
```

y analizar:

> ¿Cuál funciona mejor y por qué?

> “Random Forest ganó.”

> “Random Forest performed better, possibly because the relationships between the predictors and the target are nonlinear.”

\[
resultado + razonamiento
\]

# Debes hacer algo diferente de Kaggle

Este probablemente sea uno de los puntos más importantes para tu estrategia.

Supongamos que encuentras un notebook de Kaggle que hace:


Tu proyecto no debería ser:

```text

 ↓
StandardScaler
 ↓

 ↓
Accuracy = 87%
```

Eso sería básicamente reproducir trabajo existente.

En cambio podrías investigar:

```text
Existing Kaggle work
        ↓
What has already been tried?
        ↓
What is missing?
        ↓
Our contribution
```

Por ejemplo:

- comparar modelos que no se compararon adecuadamente,
- mejorar preprocessing,
- estudiar feature selection,
- analizar class imbalance,
- probar otro evaluation strategy,
- estudiar hyperparameters,
- comparar diferentes feature representations,
- investigar por qué un modelo falla,
- evaluar una técnica más reciente.

No significa que tengas que inventar un algoritmo nuevo.

La “originalidad” puede ser una **investigación razonable que no sea simplemente copiar lo que ya está publicado**.

```text

Our project

Comparison
          ↓
Conclusions
```

Esa probablemente sea la función más importante de Kaggle dentro del mini-project.

La parte más importante del prompt es que **no exige que el dataset diga explícitamente “control system”**. Eso ampliaría mucho la calidad de candidatos. Por ejemplo, un dataset de una planta industrial con `inputs + disturbances + sensor outputs + timestamps` puede ser mucho más valioso para **dynamic modeling/system identification** que un dataset etiquetado como “control” pero pequeño o artificial.

Para tu interés específico, yo priorizaría una estructura conceptual de proyecto como:

\[
\boxed{
[u(t),\,y(t),\,u(t-1),\,y(t-1),\ldots]
\rightarrow
y(t+1)
}
\]

o incluso:

\[
\boxed{
[\mathbf{u}(t-k:t),\,\mathbf{y}(t-k:t)]
\rightarrow
\mathbf{y}(t+h)
}
\]

Eso permitiría transformar un dataset industrial multivariable en un problema de **supervised dynamic system identification** y después comparar, por ejemplo, un modelo lineal contra KNN, árboles, Random Forest, boosting o modelos no lineales. Ese enfoque puede darle al mini-project una identidad bastante más interesante que una clasificación genérica de Kaggle.
